# 创建任务期间禁止构建/发布 — 约束说明

## 背景

当前系统里：

- 创建小程序走 `CreateNovelTaskManager`
- 构建/发布走 `TaskQueueManager`
- 三者不是同一套互斥控制

所以现状是：

- 同一时间只能有一个“创建”任务
- 但“创建”和“构建/发布”之间没有互斥

这会带来明显风险，因为创建流程会直接修改 `build.workPath` 下的本地工程文件，而正式构建/发布默认也读取同一份工程目录。

---

## 问题定义

创建小程序执行过程中，不允许再发起：

- 构建
- 发布
- 预览发布
- 任何依赖正式 `build.workPath` 源码目录稳定性的任务

否则会出现以下问题：

- 构建读取到创建过程中的中间态配置
- 发布读取到尚未完全生成的代码或资源
- 创建失败回滚时，把构建/发布正在使用的文件改回去
- `package.json`、`src/modules/mod_config/*`、主题文件、资源文件等在任务执行中被并发改写

结论：

- 代码层面当前“能触发”
- 业务层面必须“禁止触发”

---

## 目标

新增一条全局约束：

> 只要有创建任务处于运行中，就禁止正式环境的构建和发布任务启动。

返回明确错误，不进入任务队列。

---

## 约束范围

### 禁止的接口

- `POST /api/novel-build/build`
- `POST /api/novel-build/batch-build`
- `POST /api/novel-publish/publish`
- 所有正式环境发布/预览相关入口

### 可放行的接口

以下接口不依赖正式 `build.workPath`，可以视情况继续允许：

- 查询类接口
- 任务状态查询接口
- 日志查询接口
- 明确只使用 `build.testWorkPath` 的测试构建接口

注意：

- 如果某个“测试接口”内部仍然会读写正式 `build.workPath`，也必须禁止
- 是否放行测试环境构建，取决于其是否完全隔离正式源码目录

---

## 实现原则

### 原则1：在入口处拦截

不要让任务先进队列再失败。

应该在 Controller 或统一门面层直接判断：

- `CreateNovelTaskManager.getCurrentTaskId() != null`

若成立，直接返回错误：

```json
{
  "code": 400,
  "message": "当前有小程序创建任务正在执行，禁止构建或发布，请稍后再试"
}
```

这样最直接，行为也最稳定。

### 原则2：错误要可机器识别

建议统一错误码：

- `CREATE_TASK_RUNNING`

示例：

```json
{
  "code": 400,
  "message": "当前有小程序创建任务正在执行，禁止构建或发布，请稍后再试",
  "errorCode": "CREATE_TASK_RUNNING"
}
```

### 原则3：先保护正式环境

第一阶段只拦正式构建/发布即可，不要一上来改太大。

如果后续确认测试环境也会受影响，再补充到统一约束里。

---

## 推荐实现方案

### 方案A：最小改动，直接在 Controller 判断

在以下 Controller 的任务启动入口前增加判断：

- `NovelAppBuildController`
- `NovelAppPublishController`

伪代码：

```java
if (createNovelTaskManager.getCurrentTaskId() != null) {
    return Result.error("当前有小程序创建任务正在执行，禁止构建或发布，请稍后再试");
}
```

优点：

- 改动最小
- 行为直观
- 风险低

缺点：

- 判断逻辑会分散在多个入口

### 方案B：抽成统一守卫

新增一个守卫组件，例如：

- `CreateTaskGuard`

提供统一方法：

```java
public void checkNoCreateTaskRunning()
```

在 build/publish 各入口统一调用。

优点：

- 逻辑集中
- 后续扩展容易

缺点：

- 比方案A多一层封装，但依然不复杂

结论：

- Phase 1 用方案A
- Phase 2 如入口变多，再收敛到方案B

---

## 不推荐方案

### 不推荐1：依赖 TaskQueueManager 排队解决

原因：

- 创建任务根本不在 `TaskQueueManager` 里
- 两套任务系统彼此独立
- 单靠队列无法实现“创建 vs 构建/发布”的互斥

### 不推荐2：只在前端禁用按钮

原因：

- agent、脚本、第三方调用方都可以绕过前端
- 约束必须在后端保证

### 不推荐3：等构建/发布启动后再检查

原因：

- 已经进入队列或启动子进程，再失败成本更高
- 还会留下脏状态和误导性的任务记录

---

## 状态语义

这里的“创建任务运行中”定义为：

- `CreateNovelTaskManager.getCurrentTaskId() != null`

这里只要任务尚未进入 `finally` 并执行 `removeTask(...)`，都视为运行中。

也就是说以下阶段都要拦：

- 已拿到 taskId，等待异步线程启动
- 正在执行数据库写入
- 正在执行本地文件写入
- 正在执行资源文件生成
- 正在异常回滚，但尚未 `removeTask`

---

## 接口行为要求

### 构建接口

当创建任务运行中时：

- 不创建 build taskId
- 不写入队列
- 直接返回错误

### 发布接口

当创建任务运行中时：

- 不创建 publish taskId
- 不写入队列
- 不启动上传/预览逻辑
- 直接返回错误

---

## 文档与提示文案

建议统一提示文案：

`当前有小程序创建任务正在执行，禁止构建或发布，请稍后再试`

如果要更短：

`创建任务执行中，暂不允许构建或发布`

对外文档也应明确写出：

- 创建任务与构建/发布互斥
- 这是后端硬约束，不是前端限制

---

## 实施计划

### Phase 1

- 在 build 入口增加创建中拦截
- 在 publish 入口增加创建中拦截
- 返回统一错误文案

### Phase 2

- 引入统一错误码 `CREATE_TASK_RUNNING`
- 抽出公共守卫组件
- 将所有正式环境相关入口统一接入守卫

### Phase 3

- 评估测试环境接口是否也需要纳入同一互斥规则

---

## 结论

这个约束不是优化项，而是正确性要求。

因为当前创建流程会修改正式源码目录，而构建/发布依赖该目录稳定，所以：

> 创建任务运行期间，必须禁止正式构建和发布启动。

否则系统虽然“能跑”，但结果不可靠。
