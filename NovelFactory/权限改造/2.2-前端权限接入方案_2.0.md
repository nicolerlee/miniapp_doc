# 前端权限接入方案

## 一、目标

前端只做两件事：
- 登录后拿到当前用户权限列表
- 根据权限列表控制菜单、页面数据和按钮显示/拦截

后端 `@RequirePermission` 是安全底线，前端权限控制只是体验优化。

---

## 五、UI 交互逻辑

- 业务管理员在用户管理页面为用户分配角色（下拉选择：默认用户 / 产品 / 研发 / 管理员）
- 角色切换后，用户的权限立即按 `sys_role_permission` 表生效
- 前端通过 `/api/admin/permission/my` 获取当前用户的权限列表，控制菜单和按钮的显示/隐藏
- 超级管理员（`type=-1`）前端直接展示全部功能，不查权限表

## 二、权限数据获取

### 2.1 登录后拉取权限

```js
const res = await request.get('/api/admin/permission/my')
// 返回 ['agent:app:list', 'ci:build:run', 'config:ui:write', ...]
localStorage.setItem('permissions', JSON.stringify(res.data))
```

### 2.2 封装判断函数

```js
// utils/permission.js
export function getPermissions() {
  return JSON.parse(localStorage.getItem('permissions') || '[]')
}

export function hasPermission(code) {
  return getPermissions().includes(code)
}

export function hasAnyPermission(codes) {
  const permissions = getPermissions()
  return codes.some(code => permissions.includes(code))
}
```

### 2.3 建议补充

- 退出登录时清空本地权限缓存
- 切换账号后重新拉权限，不复用旧账号缓存
- 403 时提示“无权限”而不是静默失败

## 三、前端控制原则

### 3.1 四档控制策略

| 级别 | 策略 | 适用模块 |
|------|------|---------|
| 无权限 | 一级菜单不展示；入口点击时拦截并提示 | 后台管理菜单、首页功能卡片 |
| 只读权限 | 页面可进入可查看；写操作按钮置灰，点击给警告 | 配置页、列表页、详情页 |
| 数据兜底 | 页面可进入，但接口按权限返回 403 | 配置页、用户管理页、日志查看页、CodeSync 页、工具箱页

### 3.2 原则

- 无权限：不展示一级菜单，或在入口点击时直接拦截
- 只读权限：允许进入页面查看数据，但所有写操作按钮置灰
- 置灰按钮点击后统一提示：`无操作权限，请联系管理员`
- 超管专用、应急操作、高危险操作继续隐藏，不对普通用户做置灰展示
- 真正的数据安全只依赖后端，不依赖前端隐藏

## 四、菜单级改动

### 4.1 适用权限

- 用户管理 / 权限管理：`admin:user:read`
- 数据库导出：`ops:db-export:read`
- 代码同步：`sandbox:code-sync:read` 或 `ops:code-sync:read`
- 工具箱：`sandbox:toolbox:read`

### 4.2 路由守卫示例

```js
router.beforeEach((to, from, next) => {
  const requiredPermission = to.meta?.permission
  const requiredAnyPermission = to.meta?.anyPermission
  const noSinglePermission = requiredPermission && !hasPermission(requiredPermission)
  const noAnyPermission = requiredAnyPermission && !hasAnyPermission(requiredAnyPermission)
  if (noSinglePermission || noAnyPermission) {
    next('/')
    return
  }
  next()
})
```

### 4.3 路由 meta 建议

```js
{
  path: '/admin/users',
  component: UserPage,
  meta: { permission: 'admin:user:read' }
},
{
  path: '/admin/code-sync',
  component: CodeSyncPage,
  meta: {
    anyPermission: ['sandbox:code-sync:read', 'ops:code-sync:read']
  }
}
```

## 五、按钮级改动，按"只读/可操作"区分

### 5.0 按钮态原则

- 进入页面后，先区分当前用户是“只读”还是“可操作”
- 只读用户：写操作按钮全部置灰
- 可操作用户：写操作按钮正常可点击
- 完全无权限的用户不进入该页面；如果是从入口卡片点击进入，则在入口层直接拦截
- 置灰按钮必须配 tooltip 或明确文案：`无操作权限，请联系管理员`
- 超管专用、应急操作、高危险操作：无权限时直接隐藏
- 不允许出现“按钮消失但用户不知道原因”的情况

### 5.1 基础按钮示例

```html
<el-button
  :disabled="!hasPermission('agent:app:create')"
  @click="create"
>
  创建应用
</el-button>

<el-button
  :disabled="!hasPermission('config:basic:write')"
  @click="edit(row)"
>
  编辑
</el-button>

<el-button
  :disabled="!hasPermission('agent:app:delete')"
  @click="del(row)"
>
  删除
</el-button>
```

建议配合 `el-tooltip` 使用：

```html
<el-tooltip
  :disabled="hasPermission('ci:publish:run')"
  content="无操作权限，请联系管理员"
>
  <el-button
    :disabled="!hasPermission('ci:publish:run')"
    @click="publish"
  >
    发布
  </el-button>
</el-tooltip>
```

### 5.1.1 推荐判断口径

- 页面进入条件：看 `read` 权限
- 页面写操作条件：看 `write / execute` 权限
- 没有 `read`：不展示菜单，或在入口点击时直接拦截
- 有 `read` 但没有 `write / execute`：页面可看，按钮置灰

## 六、页面数据层改动

### 6.1 应用列表与详情

- 应用列表入口依赖 `/api/agent/app/list` 或对应页面公开能力
- 详情数据中的配置域按后端字段级鉴权返回，无独立 `agent:app:read` 权限点
- 没权限时：
  - 菜单可隐藏，也可保留空页面
  - 但接口返回必须由后端兜底 403

### 6.2 任务页

- `status / logs` 不使用独立权限点
- 前端只负责正常请求，是否可查看由后端按“任务创建者本人 + taskType 反查发起权限”动态鉴权
- 队列统计、排队位置接口为“已认证即可”，前端无需单独权限码

### 6.3 发布结果页

- 查看二维码、查看发布结果依赖 `ci:publish:read`

### 6.4 配置页

- 列表、详情、搜索条件加载用 `*:read`
- 创建、编辑、删除、启用等操作用 `*:write`

建议页面内部也分成两层判断：
- 进入页面前：判断是否有 `read`
- 渲染操作区：判断是否有 `write`

### 6.5 API Key 页面

- 查看列表依赖 `apikey:read`
- 创建按钮依赖 `apikey:create`
- 删除按钮依赖 `apikey:delete`

### 6.6 工具箱页面

- 查看调试信息、发版前检查依赖 `sandbox:toolbox:read`
- Retry / Repair 类执行接口依赖 `sandbox:toolbox:execute`
- `clear-running / trigger` 属于超管应急接口，不做普通权限点前端控制，不给普通角色展示入口

### 6.7 CodeSync 页面

- 页面入口：有 `sandbox:code-sync:read` 或 `ops:code-sync:read` 任一权限即可进入
- 环境切换：
  - 切到测试环境时，列表、状态、日志请求要求 `sandbox:code-sync:read`
  - 切到正式环境时，列表、状态、日志请求要求 `ops:code-sync:read`
- 操作按钮：
  - `pull / push / stash / restore-stash / switch-branch / delete-dist / install-npm / cancel-install-npm`
    - 测试环境按钮依赖 `sandbox:code-sync:execute`
    - 正式环境按钮依赖 `ops:code-sync:execute`
  - `copy-to-test` 按钮单独依赖 `sandbox:code-sync:copy-from-prod`
- `copy-status` 页面块只有同时具备 `sandbox:code-sync:read` 和 `ops:code-sync:read` 时才显示

## 七、权限管理页面（用户管理页内）

用户管理页面中，每个用户行增加「角色」列和角色切换操作：

### 7.1 UI 布局

```
┌──────────────────────────────────────────────────────────────┐
│  用户名    │ 邮箱           │ 角色         │ 状态   │ 操作   │
├──────────────────────────────────────────────────────────────┤
│  张三      │ z@example.com  │ [研发 ▼]     │ 已通过 │ 审核 删除│
│  李四      │ l@example.com  │ [产品 ▼]     │ 已通过 │ 审核 删除│
│  王五      │ w@example.com  │ [默认用户 ▼] │ 待审核 │ 审核 删除│
└──────────────────────────────────────────────────────────────┘
```

### 7.2 角色下拉选项

| 选项 | 对应 role_code | 说明 |
|------|---------------|------|
| 默认用户 | `default` | 只能查看配置，可管理自己的 API Key |
| 产品 | `product` | 能创建应用、编辑配置、构建发布 |
| 研发 | `dev` | 全部业务操作 + 运维 |
| 管理员 | `admin` | 非超管，但可管理用户 |

### 7.3 交互逻辑

- 下拉切换角色后，调用 `PUT /api/admin/user/{userId}/role` 保存
- 保存成功后该用户下次请求即按新角色的权限生效
- 仅超级管理员可见此页面和操作
- 不能修改自己的角色（防止超管把自己降级）
- 超级管理员（`type=-1`）不是下拉角色项，不通过角色下拉分配

## 八、前端实施步骤

1. 登录后调用 `/api/admin/permission/my`
2. 封装 `getPermissions / hasPermission / checkPermission`（含超管 bypass）
3. 路由表补 `meta.permission`
4. 菜单组件按 `hasPermission` 控制入口显示
5. **文曲自动化入口卡片接入权限拦截**（6 张卡片始终可见，点击守卫）
6. **测试配置中心入口卡片接入权限拦截**
7. **百宝箱首页卡片接入权限拦截**
8. 页面按钮按 `hasPermission` 控制显示
9. 配置页拆成 `read` 与 `write` 两层控制
10. 任务页按动态鉴权口径接入，发布结果页接入 `ci:publish:read`
11. 403 统一错误提示处理
12. 用户管理页面增加角色下拉切换
13. 联调验证权限覆盖是否正确

---

## 九、注意事项

1. 前端权限控制不能替代后端鉴权
2. 白名单接口即使前端不展示，也仍然可能被直接访问
3. 前端权限码必须与后端 RBAC 文档保持一致，禁止继续使用旧码如 `admin:db-export:*`、`admin:code-sync:*`、`ops:toolbox:*`、`agent:app:update`
4. 切账号、刷新 token、退出登录时要同步刷新权限缓存
