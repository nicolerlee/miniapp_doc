# 权限 UI 与接口映射（应用成员制）

## 〇、设计结论

这版不再采用 `user_app_scope`。

改成两层模型：

1. **平台级权限**
   控制“能不能进系统做全局动作”，存到 `user_permission`
2. **应用级成员权限**
   控制“在某个 app 下能做什么”，存到 `app_member + app_role + app_role_permission`

核心规则：

- 创建应用的人，创建成功后自动成为该应用的 `owner`
- `owner` 是该应用最高权限角色，天然拥有该应用全部权限
- `owner` 可以给其他人分配该应用内的角色
- 所有应用级接口，执行时都要先定位 `appId`，再判断当前用户在这个 `appId` 下的角色是否拥有对应权限

## 一、数据库表结构

### 1.1 权限定义表

```sql
CREATE TABLE permission (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    code VARCHAR(128) NOT NULL UNIQUE COMMENT '权限标识',
    name VARCHAR(64) NOT NULL COMMENT '权限名称',
    group_name VARCHAR(64) NOT NULL COMMENT '权限分组',
    scope_type VARCHAR(16) NOT NULL COMMENT 'platform/app'
);
```

说明：

- `platform`：平台级权限，只查 `user_permission`
- `app`：应用级权限，只查 `app_member -> app_role -> app_role_permission`

### 1.2 用户-平台权限关联表

```sql
CREATE TABLE user_permission (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    user_id BIGINT NOT NULL,
    permission_code VARCHAR(128) NOT NULL,
    UNIQUE KEY uk_user_perm (user_id, permission_code)
);
```

说明：

- 这张表只存平台级权限
- 不再往这里塞应用级权限

### 1.3 应用角色定义表

```sql
CREATE TABLE app_role (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    code VARCHAR(32) NOT NULL UNIQUE COMMENT 'owner/editor/viewer',
    name VARCHAR(32) NOT NULL COMMENT '角色名称',
    sort_no INT NOT NULL DEFAULT 0
);
```

推荐初始化：

```sql
INSERT INTO app_role (code, name, sort_no) VALUES
('owner',  '拥有者', 1),
('editor', '协作者', 2),
('viewer', '只读',   3);
```

### 1.4 应用角色-权限关联表

```sql
CREATE TABLE app_role_permission (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    role_code VARCHAR(32) NOT NULL,
    permission_code VARCHAR(128) NOT NULL,
    UNIQUE KEY uk_role_perm (role_code, permission_code)
);
```

说明：

- 这里只存 `scope_type='app'` 的权限
- 不存平台级权限

### 1.5 应用成员表

```sql
CREATE TABLE app_member (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    app_id BIGINT NOT NULL,
    user_id BIGINT NOT NULL,
    role_code VARCHAR(32) NOT NULL,
    created_by BIGINT NOT NULL,
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    UNIQUE KEY uk_app_user (app_id, user_id)
);
```

说明：

- 一条记录表示“某用户是某应用的一个成员”
- 真正的应用级权限，不再直接挂到用户上，而是通过 `role_code` 展开

### 1.6 废弃表

这版废弃：

- `user_app_scope`

原因：

- 它只能表达“这个用户对这个 app 是 read 还是 write”
- 表达不了“同一个 app 下，不同模块权限不同”
- 不符合“创建者是应用管理员、管理员可给他人分配应用内角色”这个产品模型

## 三、应用内角色设计

## 3.1 角色语义

| 角色 | 语义 |
|------|------|
| `owner` | 应用拥有者，也是创建者默认角色，拥有该应用全部权限 |
| `editor` | 协作者，可构建、发布、改配置、操作沙箱，但不能管成员 |
| `viewer` | 只读成员，只能看应用和相关配置、状态、结果 |

## 3.2 推荐角色权限矩阵

| 权限组 | owner | editor | viewer |
|--------|:-----:|:------:|:------:|
| 查看应用列表/详情 `agent:app:list` | ✅ | ✅ | ✅ |
| 删除应用 `agent:app:delete` | ✅ |  |  |
| 管理应用成员 `agent:member:manage` | ✅ |  |  |
| 构建/停止构建 `ci:build:*` | ✅ | ✅ |  |
| 查看发布结果/任务 `ci:publish:read` + `ci:task:read` | ✅ | ✅ | ✅ |
| 发起/停止发布 `ci:publish:run/stop` | ✅ | ✅ |  |
| 配置写权限 `config:*:write` + `version:update` | ✅ | ✅ |  |
| 配置读权限 `config:*:read` | ✅ | ✅ | ✅ |
| 沙箱写权限 `sandbox:*:write/execute/copy-from-prod` | ✅ | ✅ |  |
| 沙箱读权限 `sandbox:*:read` | ✅ | ✅ | ✅ |

说明：

- `viewer` 是真正的只读角色
- `editor` 是日常研发/运营协作者
- `owner` 是应用最高角色，也是创建者默认角色

## 3.3 创建应用的默认行为

`POST /api/agent/app/create` 成功后，后端必须额外执行：

```sql
INSERT INTO app_member (app_id, user_id, role_code, created_by)
VALUES (?, 当前登录用户, 'owner', 当前登录用户);
```

否则会出现：

- 用户能创建应用
- 但创建完之后自己却看不到、也管不了这个应用

## 五、鉴权模型

## 5.1 平台级接口

执行逻辑：

```text
用户认证通过
→ 查 permission.scope_type
→ 若为 platform
    → 查 user_permission
```

适用接口：

- 创建应用
- API Key
- 数据库导出
- 正式环境代码
- 用户管理
- 操作日志

## 5.2 应用级接口

执行逻辑：

```text
用户认证通过
→ 查 permission.scope_type
→ 若为 app
    → 从请求中拿 appId
      或通过 taskId / batchTaskId / configId 反查 appId
    → 查 app_member，拿到当前用户在该 app 下的 role_code
    → 查 app_role_permission
    → 判断该 role_code 是否拥有目标 permission_code
```

## 5.3 三类应用级接口的判断方式

### 1. 单 app 接口

例如：

- `GET /api/agent/app/detail?appId=1001`
- `POST /api/novel-ui/updateUiConfig`

做法：

- 直接从请求里取 `appId`
- 再校验该用户在这个 app 下是否有对应权限

### 2. 间接资源接口

例如：

- `GET /api/agent/task/{taskId}/status`
- `POST /api/agent/publish/stop/{taskId}`

做法：

- 先通过 `taskId` 查出所属 `appId`
- 再按 `appId` 校验

### 3. 列表接口

例如：

- `GET /api/agent/app/list`

做法：

- 不校验单个 `appId`
- 直接按当前用户在 `app_member` 中有记录的 app 做结果集过滤

SQL 示例：

```sql
SELECT a.*
FROM app a
JOIN app_member m ON a.id = m.app_id
WHERE m.user_id = ?;
```

## 8.4 统一鉴权逻辑

```text
请求进来
  → 认证通过（JWT 或 API Key）
  → AOP 拦截 @RequirePermission("xxx")
  → 从 permission 表读取该权限的 scope_type
  → 如果是 platform
      → 查 user_permission
  → 如果是 app
      → 从请求中拿 appId
        或通过 taskId / batchTaskId / configId 反查 appId
      → 查 app_member，拿到当前用户在该 app 下的 role_code
      → 查 app_role_permission，看该 role 是否拥有目标 permission_code
  → 超级管理员（type=-1）跳过检查，直接放行
  → 没有 @RequirePermission 注解的接口，已认证即可访问
```

示例：

- `POST /api/agent/app/create`
  - `@RequirePermission("agent:app:create")`
  - 平台级权限
- `GET /api/agent/app/detail?appId=1001`
  - `@RequirePermission("agent:app:list")`
  - 应用级权限
- `POST /api/novel-ui/updateUiConfig`
  - `@RequirePermission("config:ui:write")`
  - 应用级权限
- `POST /api/code-sync/pull` 且 `testEnvironment=true`
  - `@RequirePermission("sandbox:code-sync:execute")`
  - 应用级权限
- `POST /api/code-sync/pull` 且 `testEnvironment=false`
  - `@RequirePermission("ops:code-sync:execute")`
  - 平台级权限

## 九、为什么这版比 `user_app_scope` 更合适

因为你现在的真实业务规则已经不是：

- “这个用户对这个 app 是 read 还是 write”

而是：

- “这个用户是不是这个 app 的成员”
- “如果是成员，他在这个 app 里是什么角色”
- “创建者天然是 owner”
- “owner 可以给其他人分配应用内权限”

这就是标准的**应用成员制**。

所以第一性原理上，真正该落库的是：

- 成员关系
- 角色
- 角色对应的权限

而不是单独一张 `user_app_scope` 去表达 read/write。
