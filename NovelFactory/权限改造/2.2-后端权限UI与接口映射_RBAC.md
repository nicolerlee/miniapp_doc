# 权限 UI 与接口映射（RBAC 模式）

## 〇、目标与原则

### 目标

后端权限模型按 `业务功能 + 动作`， 拆成36 个权限点覆盖全部需鉴权接口，替换现有的角色粗粒度控制（`@PreAuthorize`），实现按人按需的细粒度授权。

目标只有两个：
- 权限点按业务功能拆，读写不混， 比如广告配置，支付配置
- Controller 注解、数据库权限定义、UI 权限项三者一致

### 核心原则

- 按业务功能拆，不按接口拆：一个功能 = 一个权限点，不管背后几个接口
- 按业务域分组，不按 Controller 分：前缀（`agent:`、`ci:`、`config:` 等）对应业务域
- 读写分离：`read` 和 `write`/`execute` 拆开，支持只读授权
- 特殊场景不硬塞权限点：聚合接口走字段级鉴权，异步任务走动态鉴权，超管接口直接判 `type=-1`

## 一、数据库表结构

### 权限定义表

```sql
CREATE TABLE sys_permission (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    code VARCHAR(128) NOT NULL UNIQUE COMMENT '权限标识',
    name VARCHAR(64) NOT NULL COMMENT '权限名称',
    group_name VARCHAR(64) COMMENT '分组名称'
);
```

### 角色定义表

```sql
CREATE TABLE sys_role (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    code VARCHAR(64) NOT NULL UNIQUE COMMENT '角色标识：default, product, dev, admin',
    name VARCHAR(64) NOT NULL COMMENT '角色名称',
    description VARCHAR(256) COMMENT '角色描述'
);
```

### 角色-权限关联表

```sql
CREATE TABLE sys_role_permission (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    role_code VARCHAR(64) NOT NULL,
    permission_code VARCHAR(128) NOT NULL,
    UNIQUE KEY uk_role_perm (role_code, permission_code)
);
```

### 用户-角色关联表

> RBAC 角色来源统一改为 `sys_user_role`，不再通过 `novel_user.type` 推导业务角色。
> `novel_user.type` 保留为系统身份字段，只承担“超级管理员 bypass”等系统级语义，不再承担 `default/product/dev/admin` 的角色语义。

```sql
CREATE TABLE sys_user_role (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    user_id BIGINT NOT NULL COMMENT '用户 id',
    role_code VARCHAR(64) NOT NULL COMMENT '角色标识',
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    UNIQUE KEY uk_user_role (user_id, role_code),
    KEY idx_role_code (role_code)
);
```

### 角色来源与兼容策略

- 权限解析链路统一为：`user -> sys_user_role -> sys_role_permission -> sys_permission`
- `novel_user.type=-1` 继续表示超级管理员，直接跳过权限检查
- 非超管用户的业务权限一律从 `sys_user_role` 读取，不再根据 `novel_user.type` 映射 `default/product/dev/admin`
- 迁移期允许保留旧 `type` 字段，但仅用于兼容历史代码；新代码不得再用 `type` 判断产品/研发/管理员角色
- 如果当前阶段只想支持“一人一个角色”，也仍然使用 `sys_user_role`；服务层可限制每个用户仅保留一条有效角色记录

### 3.3 配置管理

> **聚合编辑接口特殊说明**
>
> `POST /api/agent/app/update` 采用字段级鉴权，不绑定单一权限点。
> 接口内部按请求体中实际传入的配置域，动态检查对应权限：
>
> | 传入字段 | 检查的权限点 |
> |---------|-------------|
> | baseConfig | `config:base:write` |
> | paymentConfig | `config:pay:write` |
> | agentAdConfig | `config:ad:write` |
> | uiConfig | `config:ui:write` |
> | commonConfig | `config:common:write` |
>
> 未传入的字段不检查。只要用户对传入的每个配置域都有写权限，请求就通过。
> 权限管理 UI 中不单独展示这两个聚合接口，用户配置各模块的 read/write 权限即可。
>
> `GET /api/agent/app/detail` 和 `GET /api/agent/app/query` 同理：按用户拥有的 read 权限，动态决定返回哪些配置域，没权限的字段返回 null。

### 3.8 异步任务状态查询（动态鉴权，无独立权限点）

> **设计原则**：异步接口（create / build / publish / npm-install）返回 taskId 后，
> 调用方天然需要查询该任务的状态和日志。因此任务状态查询接口不设独立权限点，
> 改为在 `AgentTaskStatusService` 层做动态鉴权：**谁发起的谁能查 + taskType 反查发起权限**。

#### 涉及接口

| 接口 | 说明 |
|------|------|
| `GET /api/agent/task/{taskId}/status` | 查询任务状态 |
| `GET /api/agent/task/{taskId}/logs` | 查询任务日志 |
| `GET /api/task-queue/statistics` | 队列统计（已认证即可，不含敏感数据） |
| `GET /api/task-queue/position` | 查询任务排队位置（已认证即可） |

#### 鉴权规则（status / logs 接口）

```
请求 GET /api/agent/task/{taskId}/status 或 /logs
  → 认证通过（JWT 或 API Key）
  → 查到任务的 taskType 和 userId
  → 校验规则（按优先级）：
     1. 超级管理员（type=-1）：直接放行
     2. 任务创建者本人（当前用户 userId == 任务 userId）：直接放行
     3. 非创建者：按 taskType 检查对应的"发起权限"，有任一即放行
```

#### taskType → 权限映射

| taskType | 需要的权限（任一即可） | 说明 |
|----------|----------------------|------|
| `build` | `ci:build:run` | 有构建权限就能查构建任务状态 |
| `publish` | `ci:publish:run` | 有发布权限就能查发布任务状态 |
| `preview` | `ci:publish:run` | 预览属于发布流程 |
| `CREATE` | `agent:app:create` | 有创建应用权限就能查创建任务状态 |
| `npm-install` | `sandbox:code-sync:execute` 或 `ops:code-sync:execute` | 必须按任务环境二选一判断：test 只能用 `sandbox:code-sync:execute`，prod 只能用 `ops:code-sync:execute` |

#### 队列统计接口（statistics / position）

`GET /api/task-queue/statistics` 和 `GET /api/task-queue/position` 仅返回队列排队数量和位置信息，
不含任务详情或敏感数据，**已认证即可访问**，不做额外权限检查。

#### WebSocket 日志推送

WebSocket 订阅（`/topic/build-logs/{taskId}` 和 `/topic/novel-create-log/{taskId}`）
依赖 STOMP 连接的认证身份，与 HTTP 接口共享同一套鉴权逻辑。
前端在订阅时需携带有效的认证 token，后端在 WebSocket 拦截器中做同样的动态鉴权校验。

### 7.2.1 用户角色迁移策略

#### 原则

- 不立即删除 `novel_user.type`
- 立即停止使用 `novel_user.type` 做 RBAC 角色解析
- 超级管理员 bypass 逻辑继续保留：`novel_user.type == -1`

#### 存量数据迁移

```sql
-- 先为所有非超管用户补默认角色
INSERT IGNORE INTO sys_user_role (user_id, role_code)
SELECT id, 'default'
FROM novel_user
WHERE type != -1;

-- 再按旧 type 覆盖历史主角色（示例映射：1=product, 0=dev）
UPDATE sys_user_role ur
JOIN novel_user u ON u.id = ur.user_id
SET ur.role_code = CASE
    WHEN u.type = 1 THEN 'product'
    WHEN u.type = 0 THEN 'dev'
    ELSE 'default'
END
WHERE u.type != -1;
```

#### 迁移后的约束

- 注册：创建用户后，向 `sys_user_role` 插入 `default`
- 改角色：只更新 `sys_user_role`
- 查权限：只从 `sys_user_role` 查
- 判断超管：只看 `novel_user.type == -1`
- 历史代码中的 `type == 0/1` 角色判断全部下线

#### `novel_user.type` 如何处理

- 不废弃表字段，不做本期物理删除
- 从 RBAC 语义中移除
- 仅保留两类用途：

  - 其他历史系统身份兼容逻辑（如果还有）

#### 代码里要改掉的旧写法

- 不能再写：

### 7.4 鉴权逻辑

```
请求进来
  → 认证通过（JWT 或 API Key）
  → AOP 拦截 @RequirePermission("xxx")
  → 从 SecurityContext 拿当前用户
  → 超级管理员（type=-1）跳过检查，直接放行
  → 根据 userId 查 sys_user_role 拿到角色 code
  → 查 sys_role_permission 看角色是否有该 permission_code
  → 没有 @RequirePermission 注解的接口，已认证即可访问
  → 聚合接口（detail/update）走字段级鉴权，按传入字段动态检查
  → 任务状态接口走动态鉴权（见 3.8 节）
```

### 7.5 异步任务动态鉴权实现要点

`AgentTaskStatusService` 中新增鉴权方法，在返回任务状态前校验：

```java
/**
 * 校验当前用户是否有权查询该任务
 * @return true=放行, false=拒绝
 */
public boolean canAccessTask(String taskId, Long currentUserId, boolean isSuperAdmin) {
    // 1. 超级管理员直接放行
    if (isSuperAdmin) return true;

    // 2. 查任务信息（TaskQueueManager / CreateNovelTaskManager / DB）
    //    拿到 taskUserId、taskType、testEnvironment

    // 3. 任务创建者本人直接放行
    if (currentUserId.equals(taskUserId)) return true;

    // 4. 非创建者：按 taskType 和任务环境精确判定所需权限
    String requiredPerm = resolveRequiredPermission(taskType, testEnvironment);
    if (requiredPerm == null) return false;
    return permissionService.hasPermission(currentUserId, requiredPerm);
}

private String resolveRequiredPermission(String taskType, Boolean testEnvironment) {
    return switch (taskType) {
        case "build" -> "ci:build:run";
        case "publish", "preview" -> "ci:publish:run";
        case "CREATE" -> "agent:app:create";
        case "npm-install" -> Boolean.TRUE.equals(testEnvironment)
            ? "sandbox:code-sync:execute"
            : "ops:code-sync:execute";
        default -> null;
    };
}
```
