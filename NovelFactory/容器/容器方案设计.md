# 容器方案设计

## 核心思路

每个用户拥有独立的工作空间，所有操作（创建、编辑、构建、打包）都在自己的空间内进行，互不干扰。完成后统一合并回主库。

```
真相源(main 分支)
    ↓ git worktree
/workspaces/user_张三/   ← 用户A工作空间
/workspaces/user_李四/   ← 用户B工作空间
/workspaces/user_王五/   ← 用户C工作空间
    ↓ 提交合并
真相源(main 分支)
```

---

## 技术方案：Git Worktree

使用 Git 原生的 worktree 功能，一个仓库支持多个独立工作目录，共享底层 git 对象，磁盘占用远小于完整副本。

### 工作空间结构

```
/workspaces/
├── user_张三/
│   ├── src/
│   ├── package.json
│   ├── node_modules -> /shared/node_modules  (软链接，共享依赖)
│   └── dist/                                 (构建产物，各自独立)
├── user_李四/
│   └── ...
└── user_王五/
    └── ...
```

### node_modules 共享说明

- 所有工作空间通过软链接共享同一份 node_modules，节省磁盘，初始化快
- 适用前提：构建工具链不会写入 node_modules（无运行时缓存写入）
- 如果工具链有写入行为，需改为每个工作空间独立安装，避免互相污染

## 变更单元（change_id）

每次用户提交合并，对应一个明确的变更单元，用 change_id 标识。审批、合并、通知都针对 change_id 操作，而不是针对工作空间本身。

```
workspace 表（工作空间，按 userId 隔离）
┌─────────┬──────────────────────┬─────────────────────┬────────┐
│ user_id │ workspace_path       │ last_active_time    │ status │
└─────────┴──────────────────────┴─────────────────────┴────────┘

change 表（变更单元）
┌───────────┬─────────┬────────┬──────────────┬────────┐
│ change_id │ user_id │ branch │ submitted_at │ status │
├───────────┼─────────┼────────┼──────────────┼────────┤
│ chg_001   │ 张三    │ ...    │ 2026-04-15   │ pending│
└───────────┴─────────┴────────┴──────────────┴────────┘
```

change 状态流转：
```
editing → submitted（提交审批）→ approved（审批通过）/ rejected（拒绝）
```

## 用户操作流程

```
用户登录
  ↓
系统检查是否有工作空间
  ↓ 无则创建，有则复用，同时 dry-run 检测是否落后于主库
在工作空间内操作（创建/编辑/构建/打包）
  ↓
点击"提交合并"，生成 change_id
  ↓
系统检测冲突
  ├── 有冲突 → 展示冲突详情，用户选择保留哪个值
  └── 无冲突 → 创建待审批记录
              ↓
          管理员审批通过
              ↓
          change 合并到主库，工作空间同步到新基线
```

## 主库代码同步

用户工作空间可能落后于主库（其他人的改动已合并），登录时先做 dry-run 检测：

```
用户登录
  ↓
dry-run 检测工作空间是否落后于主库
  ├── 没有落后 → 直接进入，无感知
  └── 有落后   → 执行 merge
                  ├── 无冲突 → 用户无感知，直接进入
                  └── 有冲突 → 提示用户处理冲突
```

dry-run 先于实际 merge 执行，避免直接 merge 失败导致工作空间状态混乱。只有真正冲突时才打扰用户。

---

## 冲突处理策略

冲突处理**明确限定为结构化配置文件**（JSON/YAML），不适用于任意文件类型。

- 检测到冲突 → abort merge，恢复工作空间到冲突前状态
- 返回冲突详情，前端展示对比让用户选择
- 用户逐一确认后重新提交
- 非结构化文件（模板、代码文件等）发生冲突时，提示用户联系管理员手动处理

冲突展示示例：
```
⚠️ 发现冲突，请处理后重新提交

配置项：首页背景色
  主库当前值：#FF0000
  你的修改值：#00FF00

  [使用主库的值]  [保留我的值]
```

## 审批通过后的工作空间处理

审批通过后，当前 change 关闭，工作空间自动同步到最新主线基线，用户在新基线上继续工作：

```
管理员审批通过
  ↓
change_001 合并进 main，状态置为 approved
  ↓
工作空间基于最新 main 切换到新基线（change_002 的起点）
  ↓
WebSocket 推送通知用户："上次提交已合并到主库 ✅，工作区已更新"
  ↓
用户在新基线上继续编辑，下次提交为 change_002
```

worktree 目录不变，只是底层 git 分支切换到新基线，用户无感知。这样下次提交合并时冲突概率更低。

## 工作空间生命周期

| 状态 | 触发条件 | 处理 |
|------|----------|------|
| 创建 | 用户首次登录或无工作空间 | git worktree add |
| 复用 | 用户再次登录且有工作空间 | 直接使用，dry-run 检测同步 |
| 销毁 | 超过 7 天无任何操作 | git worktree remove |

用户每次操作（编辑、构建、提交等）都更新 `last_active_time`，7 天内有操作就不会被清理。

### 超时回收保护

定时任务回收前，先检查是否有未提交改动：

```java
String status = exec("git", "-C", workspacePath, "status", "--porcelain");
if (!status.isEmpty()) {
    // 有未提交改动，不回收，发通知提醒用户
    notifyService.send(userId, "您的工作空间即将过期，请尽快提交");
} else {
    exec("git", "worktree", "remove", workspacePath);
}
```

### API 调用时的工作空间检查

每个 API 进来先校验工作空间状态，不存在时自动创建（按需分配）：

```java
WorkSpace ws = workspaceService.getByUserId(userId);
if (ws == null || ws.getStatus() == DESTROYED) {
    ws = workspaceService.create(userId); // 自动创建，对调用方透明
}
```

## 后端 API 汇总

所有 git 操作由后端封装成接口，用户无需接触任何 git 命令。

### 工作空间管理

| 接口 | 说明 |
|------|------|
| `POST /api/workspace/sync` | 登录时 dry-run 检测并同步主库最新代码 |
| `DELETE /api/workspace/destroy` | 回收工作空间（超时清理时调用） |

### 构建与打包

复用现有接口，新增 `userId` 参数，后端根据 userId 查表找到对应 workspace_path，切换目录执行，其他逻辑不变。

| 接口 | 说明 |
|------|------|
| `POST /agent/build` | 原有接口，新增 userId 参数，切换到用户工作空间目录执行 |
| `POST /agent/publish` | 原有接口，新增 userId 参数，切换到用户工作空间目录执行 |

### 合并与审批

| 接口 | 说明 |
|------|------|
| `POST /api/workspace/merge` | 用户提交合并请求，生成 change_id |
| `POST /api/workspace/approve` | 管理员审批通过，合并到主库，工作空间切换新基线 |
| `POST /api/workspace/reject` | 管理员拒绝，通知用户原因 |

### 冲突处理

| 接口 | 说明 |
|------|------|
| `GET /api/workspace/conflicts` | 拉取冲突列表，返回每个冲突字段的主库值和用户值 |
| `POST /api/workspace/resolve` | 用户选择保留哪个值，body: `{ field, useMain }` |

## 网页端交互设计

### 工作空间状态栏

页面顶部始终展示当前工作空间状态：

```
┌──────────────────────────────────────────────────────┐
│  工作空间：进行中   最后操作：2小时前   [提交合并] [放弃]  │
└──────────────────────────────────────────────────────┘
```

### 三种状态对应交互

**无工作空间：**
```
[开始编辑] ← 点击后自动创建 worktree，同步主库最新代码
```

**有工作空间，主库有更新：**
```
dry-run 检测到落后，自动执行 merge
  └── 同步成功 → 无感知继续
  └── 有冲突  → 弹出冲突处理面板
```

**有工作空间，正常状态：**
```
直接进入，所有操作正常可用，右上角始终有 [提交合并] 按钮
```

### 审批通过后的交互

```
管理员审批通过
  ↓
后端 merge 到主库，工作区切换到新基线
  ↓
WebSocket 推送消息给用户
  ↓
页面角落弹出提示："上次提交已合并到主库 ✅，工作区已更新"
用户继续在新基线上操作，不受影响
```
