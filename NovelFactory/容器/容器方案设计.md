# 容器方案设计

## 核心思路

每个用户拥有独立的工作空间，所有操作（创建、编辑、构建、打包）都在自己的空间内进行，互不干扰。完成后统一合并回主库。

```
真相源(main 分支)
    ↓ git worktree
/workspaces/user_张三/   ← 用户A工作空间
/workspaces/user_李四/   ← 用户B工作空间
/workspaces/user_王五/   ← 用户C工作空间
    ↓ 提交合并
真相源(main 分支)
```

---

## 技术方案：Git Worktree

使用 Git 原生的 worktree 功能，一个仓库支持多个独立工作目录，共享底层 git 对象，磁盘占用远小于完整副本。

### 工作空间结构

```
/workspaces/
├── user_张三/
│   ├── src/
│   ├── package.json
│   ├── node_modules/          (硬链接复制自模板，各自独立)
│   └── dist/                  (构建产物，各自独立)
├── user_李四/
│   └── ...
└── user_王五/
    └── ...
```

### node_modules 依赖管理：模板硬链接复制

每个工作空间拥有独立的 node_modules 目录，构建完全并行，互不影响。通过硬链接复制（`cp -al`）实现秒级初始化和极低磁盘占用。

#### 为什么不用软链接共享 node_modules

原方案中所有工作空间通过软链接指向同一个 node_modules 目录。问题在于：构建工具（vite 等）会在 node_modules 下创建 `.vite/` 等缓存目录，多个用户并发构建时会互相覆盖缓存，导致构建出错。要解决这个问题就必须构建排队，但我们希望每个用户能独立并行构建，不需要等待。

#### 解决方案：模板 node_modules + 硬链接复制

维护一份预装好的"模板 node_modules"，每次创建工作空间时通过 `cp -al` 硬链接复制到用户目录。

```
/templates/
└── node_modules/          ← 预装好的模板，定期更新

创建工作空间时：
  cp -al /templates/node_modules /workspaces/user_xxx/node_modules
```

#### `cp -al` 的原理

`cp -al` 创建的是硬链接副本，不是真正复制文件内容：
- 每个用户的 node_modules 看起来是独立的完整目录
- 但底层文件（vue、uniapp 等包的源码）通过硬链接指向模板中的同一份数据，不占额外磁盘
- 构建工具写入的缓存文件（`.vite/` 等）是在各自用户目录下新创建的文件，和其他用户无关

```
/templates/node_modules/vue/index.js        ← 真实文件（磁盘上只有这一份）
/workspaces/user_A/node_modules/vue/index.js ← 硬链接（不占额外空间，只读）
/workspaces/user_B/node_modules/vue/index.js ← 硬链接（不占额外空间，只读）

/workspaces/user_A/node_modules/.vite/xxx   ← 用户A构建时新创建的缓存，A独有
/workspaces/user_B/node_modules/.vite/yyy   ← 用户B构建时新创建的缓存，B独有
```

#### 速度与磁盘对比

| 方案 | 初始化速度 | 20个用户磁盘占用 |
|------|-----------|-----------------|
| 每个用户 npm install | 1-2 分钟 | 20 × 500MB = 10GB |
| 软链接共享（并发构建会冲突） | 瞬时 | 500MB |
| `cp -al` 硬链接复制 | < 1 秒 | ~500MB + 少量缓存 |

#### 模板维护

模板 node_modules 需要在以下时机更新：

```bash
# 当 package.json 有变更时，重新生成模板
cd /templates
cp package.json package-lock.json ./
npm install
```

可以通过 CI/CD 或定时任务自动化：当主库的 package.json 发生变更时，自动重新生成模板。

#### 工作空间初始化

```bash
# 1. 创建 worktree
git worktree add /workspaces/user_xxx -b user_xxx_branch

# 2. 硬链接复制 node_modules（< 1秒）
cp -al /templates/node_modules /workspaces/user_xxx/node_modules
```

用户登录后秒级进入工作空间，无需等待依赖安装。

## Git 并发操作安全

### 不会互相锁的操作（用户日常操作）

每个 worktree 有自己独立的 index 文件（`.git/worktrees/user_xxx/index`），以下操作各自独立，不会互相阻塞：

| 操作 | 说明 |
|------|------|
| `git add` | 写自己的 index，不锁 |
| `git commit` | 写自己的 index + 创建 object，不锁 |
| `git status` | 读自己的 index，不锁 |
| `git diff` | 读自己的 index，不锁 |

### 会锁的操作（全局操作）

以下操作需要写共享的 `.git` 目录下的全局数据，多人同时执行会报锁冲突：

| 操作 | 说明 |
|------|------|
| `git merge` 到 main | 写全局分支引用 |
| `git fetch` | 拉取远程数据到全局 |
| `git gc` | 压缩全局对象库 |

### 解决方案：全局操作串行队列

这些全局操作都是后端在特定时机执行的（不是用户直接触发），通过一把锁控制同一时间只有一个全局操作在执行。用户的日常操作（编辑、构建、预览）完全不受影响，只有"提交合并到主库"这一步需要排队。

```java
// 全局 git 操作锁（单机用 ReentrantLock，多机用 Redis 分布式锁）
private final Lock gitGlobalLock = new ReentrantLock();

// 用户提交合并 → 需要操作 main 分支
public MergeResult mergeToMain(String changeId) {
    gitGlobalLock.lock();
    try {
        // 1. git fetch 最新
        // 2. git merge 用户分支到 main
        // 3. 检测冲突，返回结果
    } finally {
        gitGlobalLock.unlock();
    }
}

// 定时 gc（凌晨执行，避免影响用户）
@Scheduled(cron = "0 0 3 * * ?")
public void scheduledGc() {
    gitGlobalLock.lock();
    try {
        exec("git", "gc", "--auto");
    } finally {
        gitGlobalLock.unlock();
    }
}
```

**用户感知**：点击"提交合并"后看到 loading，通常 1-2 秒完成。如果前面有人在排队，多等几秒。用户不会感知到排队过程。

**注意**：排队只针对"合并到主库"这一步。编辑、构建、预览等操作完全并行，不排队。

### sync 接口幂等保护

`POST /api/workspace/sync` 接口增加幂等保护，防止用户快速刷新时重复触发 merge：

```java
public SyncResult syncWorkspace(String userId) {
    String lockKey = "sync:" + userId;
    if (!tryLock(lockKey, 30, TimeUnit.SECONDS)) {
        return SyncResult.alreadyInProgress(); // 正在同步中，直接返回
    }
    try {
        // 执行 dry-run 检测和 merge
    } finally {
        unlock(lockKey);
    }
}
```

## 变更单元（change_id）

每次用户提交合并，对应一个明确的变更单元，用 change_id 标识。审批、合并、通知都针对 change_id 操作，而不是针对工作空间本身。

```
workspace 表（工作空间，按 userId 隔离）
┌─────────┬──────────────────────┬─────────────────────┬────────┐
│ user_id │ workspace_path       │ last_active_time    │ status │
└─────────┴──────────────────────┴─────────────────────┴────────┘

change 表（变更单元）
┌───────────┬─────────┬────────┬──────────────┬────────┐
│ change_id │ user_id │ branch │ submitted_at │ status │
├───────────┼─────────┼────────┼──────────────┼────────┤
│ chg_001   │ 张三    │ ...    │ 2026-04-15   │ pending│
└───────────┴─────────┴────────┴──────────────┴────────┘
```

change 状态流转：
```
editing → submitted（提交审批）→ approved（审批通过）/ rejected（拒绝）
```

## 用户操作流程

```
用户登录
  ↓
系统检查是否有工作空间
  ↓ 无则创建（worktree + cp -al），有则复用，同时 dry-run 检测是否落后于主库
在工作空间内操作（创建/编辑/构建/打包）← 完全并行，不排队
  ↓
点击"提交合并"，生成 change_id
  ↓
系统检测冲突
  ├── 有冲突 → 展示冲突详情，用户选择保留哪个值
  └── 无冲突 → 创建待审批记录
              ↓
          管理员审批通过
              ↓
          change 合并到主库，工作空间同步到新基线
```

## 主库代码同步

用户工作空间可能落后于主库（其他人的改动已合并），登录时先做 dry-run 检测：

```
用户登录
  ↓
dry-run 检测工作空间是否落后于主库
  ├── 没有落后 → 直接进入，无感知
  └── 有落后   → 执行 merge
                  ├── 无冲突 → 用户无感知，直接进入
                  └── 有冲突 → 提示用户处理冲突
```

dry-run 先于实际 merge 执行，避免直接 merge 失败导致工作空间状态混乱。只有真正冲突时才打扰用户。

---

## 冲突处理策略

冲突分为两类，需要区分处理：

### 1. git 锁冲突（技术层面）

两个人同时执行 git merge 命令，争抢 `.git/index.lock` 文件。通过上述全局操作串行队列解决，用户无感知。

### 2. 内容冲突（业务层面）

两个人都改了同一个配置文件的同一个字段。这是任何方案都无法避免的，必须由用户做选择。

串行队列反而让内容冲突检测更可靠——张三一定先合完，李四才开始合，所以李四一定能看到张三的最新改动，冲突检测是准确的。

内容冲突处理**明确限定为结构化配置文件**（JSON/YAML），不适用于任意文件类型。

- 检测到冲突 → abort merge，恢复工作空间到冲突前状态
- 返回冲突详情，前端展示对比让用户选择
- 用户逐一确认后重新提交
- 非结构化文件（模板、代码文件等）发生冲突时，提示用户联系管理员手动处理

冲突展示示例：
```
⚠️ 发现冲突，请处理后重新提交

配置项：首页背景色
  主库当前值：#FF0000
  你的修改值：#00FF00

  [使用主库的值]  [保留我的值]
```

## 审批通过后的工作空间处理

审批通过后，当前 change 关闭，工作空间自动同步到最新主线基线，用户在新基线上继续工作。

### 操作步骤与原子性保障

approve 接口需要执行多个步骤，通过数据库事务 + 补偿机制保证一致性：

```java
@Transactional
public ApproveResult approve(String changeId) {
    // 1. 数据库：change 状态置为 approved
    changeService.updateStatus(changeId, APPROVED);

    // 2. git：merge 到 main（在全局锁内执行）
    gitGlobalLock.lock();
    try {
        gitService.mergeToMain(changeId);
    } catch (Exception e) {
        // merge 失败，事务回滚，change 状态恢复
        throw new MergeFailedException(e);
    } finally {
        gitGlobalLock.unlock();
    }

    // 3. 工作空间切换到新基线
    workspaceService.rebaseToLatestMain(changeId);

    // 4. WebSocket 推送通知用户
    wsService.notify(changeId, "上次提交已合并到主库 ✅，工作区已更新");
}
```

如果步骤 3（切换基线）失败，不影响主库数据，用户下次登录时 sync 接口会自动修复。
如果步骤 4（通知）失败，不影响数据一致性，用户下次进入时会看到最新状态。

worktree 目录不变，只是底层 git 分支切换到新基线，用户无感知。这样下次提交合并时冲突概率更低。

## 工作空间生命周期

| 状态 | 触发条件 | 处理 |
|------|----------|------|
| 创建 | 用户首次登录或无工作空间 | git worktree add + cp -al node_modules |
| 复用 | 用户再次登录且有工作空间 | 直接使用，dry-run 检测同步 |
| 销毁 | 超过 7 天无任何操作 | git worktree remove |

用户每次操作（编辑、构建、提交等）都更新 `last_active_time`，7 天内有操作就不会被清理。

### 超时回收保护

定时任务回收前，先检查是否有未提交改动：

```java
String status = exec("git", "-C", workspacePath, "status", "--porcelain");
if (!status.isEmpty()) {
    // 有未提交改动，不回收，发通知提醒用户
    notifyService.send(userId, "您的工作空间即将过期，请尽快提交");
} else {
    exec("git", "worktree", "remove", workspacePath);
}
```

### API 调用时的工作空间检查

每个 API 进来先校验工作空间状态，不存在时自动创建（按需分配）：

```java
WorkSpace ws = workspaceService.getByUserId(userId);
if (ws == null || ws.getStatus() == DESTROYED) {
    ws = workspaceService.create(userId); // 自动创建，对调用方透明
}
```

## 后端 API 汇总

所有 git 操作由后端封装成接口，用户无需接触任何 git 命令。

### 工作空间管理

| 接口 | 说明 |
|------|------|
| `POST /api/workspace/sync` | 登录时 dry-run 检测并同步主库最新代码（幂等） |
| `DELETE /api/workspace/destroy` | 回收工作空间（超时清理时调用） |

### 构建与打包

复用现有接口，新增 `userId` 参数，后端根据 userId 查表找到对应 workspace_path，切换目录执行，其他逻辑不变。构建完全并行，不排队。

| 接口 | 说明 |
|------|------|
| `POST /agent/build` | 原有接口，新增 userId 参数，切换到用户工作空间目录执行 |
| `POST /agent/publish` | 原有接口，新增 userId 参数，切换到用户工作空间目录执行 |

### 合并与审批

| 接口 | 说明 |
|------|------|
| `POST /api/workspace/merge` | 用户提交合并请求，生成 change_id（全局锁内串行执行） |
| `POST /api/workspace/approve` | 管理员审批通过，合并到主库，工作空间切换新基线 |
| `POST /api/workspace/reject` | 管理员拒绝，通知用户原因 |

### 冲突处理

| 接口 | 说明 |
|------|------|
| `GET /api/workspace/conflicts` | 拉取冲突列表，返回每个冲突字段的主库值和用户值 |
| `POST /api/workspace/resolve` | 用户选择保留哪个值，body: `{ field, useMain }` |

## 网页端交互设计

### 工作空间状态栏

页面顶部始终展示当前工作空间状态：

```
┌────────────────────────────────────────────────────────────────────┐
│  工作空间：进行中   有未提交改动   最后操作：2小时前   [提交合并] [放弃]  │
└────────────────────────────────────────────────────────────────────┘
```

### 四种状态对应交互

**无工作空间：**
```
[开始编辑] ← 点击后自动创建 worktree + cp -al node_modules，同步主库最新代码
```

**有工作空间，主库有更新：**
```
dry-run 检测到落后，自动执行 merge
  └── 同步成功 → 无感知继续
  └── 有冲突  → 弹出冲突处理面板
```

**有工作空间，有未提交改动：**
```
状态栏显示"有未提交改动"，提醒用户及时提交
右上角始终有 [提交合并] 按钮
```

**有工作空间，正常状态：**
```
直接进入，所有操作正常可用，右上角始终有 [提交合并] 按钮
```

### 审批通过后的交互

```
管理员审批通过
  ↓
后端 merge 到主库，工作区切换到新基线
  ↓
WebSocket 推送消息给用户
  ↓
页面角落弹出提示："上次提交已合并到主库 ✅，工作区已更新"
用户继续在新基线上操作，不受影响
```

## 规模扩展参考

当前方案（Git Worktree + 模板硬链接复制）适用于 100 人以内的并发场景。如果未来用户规模增长，可按以下路径演进：

| 并发用户数 | 推荐方案 |
|-----------|---------|
| < 100人 | Git Worktree + cp -al（当前方案） |
| 100-1000人 | 按需 Docker 容器 + 构建队列 |
| > 1000人 | K8s + Pod 按需调度 / 云厂商 Serverless 构建 |
