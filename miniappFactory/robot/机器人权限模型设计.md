# 机器人权限模型设计

## 1. 背景与本期目标

现有系统是典型的 `用户 -> 角色 -> 权限码` 模型，能解决“有没有某个功能权限”，但解决不了“能操作哪些项目”。

当前痛点：

- 角色粒度过粗，`builder` 一类角色把构建、编辑、上传等能力绑在一起，组合不灵活
- 权限只有全局语义，没有资源语义，无法表达“用户 A 能发 `pkg_001`，但不能发 `pkg_002`”
- 新项目上传后缺少独立审核状态，导致“项目是否审核通过”和“谁有权限操作项目”混在一起

本期目标：

- 引入“机器人”概念，允许一个用户绑定多个权限模板
- 让权限支持 `packageId` 级别的资源范围
- 给“发布”链路增加独立审核卡点，新项目默认不可发布
- 数据库物理表直接切到 `robot*` / `user_robot` 命名，旧 `sys_*` 表后续统一删除

本期非目标：

- 不做字段级权限
- 不做用户级别的项目隔离（例如用户 1 只能操作 A，用户 2 只能操作 B）
- 不做平台 / 环境 / 客户等多维复合 scope 规则引擎

一句话定义：

```
用户 -> 绑定多个机器人
机器人 = 权限集合 + 项目范围
发布 = 机器人鉴权通过 + 项目审核通过
```

## 2. 核心模型

### 2.1 机器人是什么

机器人是“带资源范围的权限模板”，本质上仍然是角色模型的升级版。

每个机器人包含两部分：

- **权限集合**：例如 `ci:build:run`、`ci:publish:submit`
- **作用范围**：这个机器人能覆盖哪些 `packageId`

### 2.2 关键原则

#### 原则 1：鉴权单元必须是“同一个机器人”

授权判断不能写成：

```text
用户所有机器人的权限并集 是否包含 P
AND
用户所有机器人的 scope 并集 是否包含 packageId
```

因为这样会产生跨机器人拼接越权。

正确写法必须是：

```text
存在某个已绑定机器人 R：
  R 包含权限 P
  且 R 覆盖 packageId
```

也就是：

```
授权成功 <=> ∃ robot
  hasPermission(robot, permissionCode)
  && inScope(robot, packageId)
```

推荐直接按 `EXISTS` 语义落 SQL，避免开发把它误翻译成“两次并集查询”：

```sql
SELECT 1
FROM user_robot ur
JOIN robot r
  ON ur.robot_code = r.code
 AND r.enabled = 1
JOIN robot_permission rp
  ON rp.robot_code = r.code
LEFT JOIN robot_scope s
  ON s.robot_code = r.code
 AND s.resource_type = 'PACKAGE'
WHERE ur.user_id = ?
  AND (rp.permission_code = ? OR rp.permission_code = '*')
  AND (
    r.scope_mode = 'ALL'
    OR s.resource_id = ?
  )
LIMIT 1;
```

这条 SQL 的关键点：

- `rp`、`r`、`s` 都挂在同一条 `robot_code` 上
- `permission` 和 `scope` 是同一个机器人闭包内共同满足
- `admin` 也是通过 `* + ALL` 命中，不走代码层 short-circuit

`permission_code='*'` 的语义必须写死为：

- 视为拥有所有原子权限
- 既覆盖 `agent:app:read`，也覆盖 `agent:app:read_unapproved`
- 已经配置 `*` 的机器人，不再额外插具体权限码记录

这样可以避免：

- 开发误以为 `*` 不覆盖新增权限点
- 同一个机器人同时存在 `*` 和具体权限码记录，导致查询重复和维护混乱

#### 原则 2：项目审核状态和机器人 scope 必须分离

`scope` 表达的是“谁能操作哪些项目”，不是“项目是否审核通过”。

项目是否可发布，应该是项目自身状态：

- `PENDING`
- `APPROVED`
- `REJECTED`

发布时同时校验：

1. 用户是否有对应发布权限
2. 该机器人是否覆盖当前 `packageId`
3. 项目审核状态是否为 `APPROVED`

#### 原则 3：`/permission/my` 只能做粗粒度能力判断

`/api/admin/permission/my` 返回的仍然是权限码集合，它只能回答：

- 用户有没有“进入某个页面/看到某类按钮”的大类能力

它不能回答：

- 用户能不能操作某一个具体 `packageId`

所以资源级控制不能继续只靠前端拿权限码数组自行判断，必须由后端做最终裁决。

执行规则写死为：

- 只要交互对象是某个具体 `packageId`
- 前端就不准依赖 `/api/admin/permission/my` 单独做放行判断
- 最终是否可操作必须以后端资源级鉴权结果为准

#### 原则 4：项目“可见性”和“可操作性”分离

系统里至少有两类读规则：

- **可见性**：用户能不能在列表/详情里看到这个项目
- **可操作性**：用户能不能对这个项目执行 build / publish / delete 等动作

本期补一条独立权限：

- `agent:app:read`：可以读取项目
- `agent:app:read_unapproved`：额外允许读取 `PENDING / REJECTED` 项目

因此：

- 只有 `agent:app:read`，默认只能看到 `APPROVED` 项目
- 同一个机器人同时拥有 `agent:app:read + agent:app:read_unapproved`，才允许看到未审核项目
- “能看到未审核项目”不等于“能发布未审核项目”

这条规则仍然遵守“同一机器人闭包”：

```text
可见未审核项目 <=> ∃ robot
  hasPermission(robot, 'agent:app:read')
  && hasPermission(robot, 'agent:app:read_unapproved')
  && inScope(robot, packageId)
```

#### 原则 5：admin 也是机器人，不走特判旁路

`admin` 应当是一台预置机器人：

- 权限：`*`
- `scope_mode=ALL`
- 参与正常的匹配、日志、审计链路

这样做的目的：

- 管理员操作也能产出完整 `auth_context`
- 不会因为代码里写了 `if (isAdmin()) return true` 而绕开统一判定
- 后续回收权限、审计归因、迁移切流都更一致

#### 原则 6：数据库物理命名与业务概念保持一致

本期数据库物理表直接使用机器人命名：

- `robot`
- `robot_permission`
- `robot_scope`
- `user_robot`

不再继续沿用 `sys_role*` / `sys_user_role` 这套旧命名。

这样做的目的：

- 避免“产品上叫机器人，数据库里叫 role”的长期认知分裂
- 后续代码、日志、管理台文案全部统一
- 切换完成后可以直接清理旧 `sys_*` 表，不再保留双重语义

## 3. 鉴权规则

### 3.1 单项目操作

适用于：

- `GET /api/app/{packageId}`
- `PATCH /api/app/{packageId}`
- `POST /api/app/{packageId}/build`
- `POST /api/app/{packageId}/publish`
- `DELETE /api/app/{packageId}`

统一判定公式：

```java
boolean isAuthorized(Long userId, String permissionCode, String packageId) {
    List<Robot> robots = loadUserRobots(userId);
    for (Robot robot : robots) {
        if (!robot.isEnabled()) {
            continue;
        }
        if (!robot.hasPermission(permissionCode) && !robot.hasPermission("*")) {
            continue;
        }
        if (robot.scopeMode == ALL) {
            return true;
        }
        if (robot.scopeMode == CUSTOM && robot.scopes.contains(packageId)) {
            return true;
        }
    }
    return false;
}
```

实现要求：

- 不允许代码层 `admin` 特判直接返回 true
- `admin` 只能通过预置机器人 `* + ALL` 命中
- 推荐把上面的 SQL 样板直接落为 Mapper/Repository 层的存在性查询

### 3.2 发布操作

发布在资源鉴权之外，额外检查项目审核状态：

```java
assertAuthorized(userId, publishPermission, packageId);
assertPackageReviewStatus(packageId, APPROVED);
```

说明：

- `preview` 和 `submit` 共用同一套 scope 判定
- “审核通过”不是往某个机器人 scope 里插一条记录
- 机器人 scope 只决定“这个用户有没有权发这个项目”
- 本期只有 `publish` 链路检查 `review_status`
- `upload / edit / install / build / deleteDist` 本期不检查 `review_status`

这意味着本期的产品边界是：

- 未审核项目允许继续编辑、安装、构建，方便研发联调
- 未审核项目不允许发布
- 如果后续产品要求“未审核也不能构建”，再单独把 `review_status` 检查上移到 `build`

### 3.3 列表与批量接口

#### 列表接口

`GET /api/app/list` 是统一项目列表入口，不能再无脑返回全量数据。

建议规则：

- 支持可选查询参数：`reviewStatus=APPROVED|PENDING|REJECTED|ALL`
- 不传 `reviewStatus` 时，返回“当前用户可见的全部项目”
- 传了 `reviewStatus` 时，只在“当前用户可见集合”内做二次筛选
- `reviewStatus` 只是筛选条件，不是越权查看开关
- 只返回当前用户在资源级判定后“可见”的项目
- 每一行返回当前项目的资源级 `allowedPermissions`
- `reviewStatus` 作为独立业务状态字段返回，不混入权限码集合

可见性规则：

- `reviewStatus=APPROVED`
  - 只要求同一个机器人拥有 `agent:app:read` 且 scope 命中
- `reviewStatus=PENDING/REJECTED`
  - 要求同一个机器人同时拥有 `agent:app:read + agent:app:read_unapproved` 且 scope 命中

接口行为明确为：

- 管理员请求 `/api/app/list`
  - 默认返回所有状态项目
- 普通查看用户请求 `/api/app/list`
  - 默认只返回 `APPROVED` 项目
- 普通查看用户请求 `/api/app/list?reviewStatus=PENDING`
  - 返回空列表，或按产品约定返回 `403`
  - 但绝不能因为传了参数就看到未审核项目
- 审核员/研发请求 `/api/app/list?reviewStatus=PENDING`
  - 返回自己可见范围内的待审核项目

推荐默认策略：

- 普通列表页统一调用 `/api/app/list`
- 审核中心调用 `/api/app/list?reviewStatus=PENDING`，或调用专用接口 `GET /api/admin/package/review/pending`

性能优化建议：

- 列表接口先判定当前用户是否绑定了任何 `scope_mode=ALL` 且拥有 `agent:app:read` 的机器人
- 如果有，再进一步判定是否拥有 `agent:app:read_unapproved`
- 命中上述条件时，可以直接走 `miniapp_package` 的状态过滤查询，不必对项目表每一行都跑一次 `EXISTS`
- 只有 `scope_mode=CUSTOM` 用户，才走 `robot_scope(resource_type, resource_id)` 索引过滤

推荐列表过滤 SQL 写成：

```sql
SELECT p.*
FROM miniapp_package p
WHERE EXISTS (
  SELECT 1
  FROM user_robot ur
  JOIN robot r
    ON ur.robot_code = r.code
   AND r.enabled = 1
  JOIN robot_permission rp_read
    ON rp_read.robot_code = r.code
   AND (rp_read.permission_code = 'agent:app:read' OR rp_read.permission_code = '*')
  LEFT JOIN robot_permission rp_read_unapproved
    ON rp_read_unapproved.robot_code = r.code
   AND (rp_read_unapproved.permission_code = 'agent:app:read_unapproved' OR rp_read_unapproved.permission_code = '*')
  LEFT JOIN robot_scope s
    ON s.robot_code = r.code
   AND s.resource_type = 'PACKAGE'
  WHERE ur.user_id = ?
    AND (
      r.scope_mode = 'ALL'
      OR s.resource_id = p.package_id
    )
    AND (
      p.review_status = 'APPROVED'
      OR rp_read_unapproved.robot_code IS NOT NULL
    )
);
```

如果支持 `reviewStatus` 查询参数，推荐在上述可见性过滤外，再追加：

```sql
AND (
  :reviewStatus IS NULL
  OR :reviewStatus = 'ALL'
  OR p.review_status = :reviewStatus
)
```

示例：

```json
{
  "packageId": "pkg_001",
  "name": "星辰文鉴",
  "reviewStatus": "APPROVED",
  "allowedPermissions": [
    "agent:app:read",
    "agent:app:write",
    "ci:build:run"
  ]
}
```

这样做的目的：

- 避免 `allowedActions.read/write/build/...` 和真实权限码命名漂移
- 新增权限码时不需要再维护一份平行布尔字段映射表
- 前端拿到的就是项目级最终判定结果

#### 详情接口

`GET /api/app/{packageId}` 和列表使用同一套可见性规则：

- 用户对该项目不可见时，后端不返回详情
- 返回 `404` 还是 `403` 由服务端统一决定

本期建议：

- 对不可见项目返回 `404`
- 避免泄露“这个项目存在但你没权限看”的信息

#### 批量接口

`batch-build`、`batch-publish` 不能只做一次总鉴权，必须逐个 `packageId` 判定。

批量接口要分两层结果：

- **同步阶段**：鉴权 + 审核状态校验
- **异步阶段**：真正执行构建/发布后的业务结果，走任务查询接口，不混在同一次响应里

同步阶段返回值建议改成：

```json
{
  "accepted": ["pkg_001", "pkg_003"],
  "rejected": [
    {"packageId": "pkg_002", "reason": "NO_SCOPE"},
    {"packageId": "pkg_004", "reason": "REVIEW_PENDING"}
  ]
}
```

`reason` 建议固定枚举为：

- `NO_PERMISSION`
- `NO_SCOPE`
- `REVIEW_PENDING`
- `REVIEW_REJECTED`
- `NOT_FOUND`
- `DISABLED_ROLE`

#### 任务结果/二维码接口

像发布二维码、任务状态这类“按 taskId 查询”的接口，不能因为 URL 里没有 `packageId` 就跳过 scope。

必须先通过任务反查资源，再按资源做鉴权。

注意这里不是永远 `1:1`：

- 单包任务：`taskId -> 1 个 packageId`
- 批量任务：`batchTaskId -> N 个 packageId`

实现要求：

- 单任务接口：反查出 1 个 `packageId` 后再判定
- 批量任务接口：必须对关联到的每一个 `packageId` 单独判定
- 不能只拿 batch 里的第一个项目做一次鉴权后放行整个批次
- `ci:publish:read` 按发布机器人自己的 `scope` 过滤
- 也就是说，用户只能查看自己被授权项目的发布结果、二维码和批量发布结果

## 4. 机器人定义

### 4.1 预置机器人

本期建议内置以下机器人：

| 机器人 | 权限 | scope | 说明 |
|--------|------|-------|------|
| `viewer` | `agent:app:read` | `ALL` | 新用户默认绑定，只能看项目 |
| `builder_global` | `agent:app:read`, `agent:app:read_unapproved`, `agent:app:upload`, `agent:app:write`, `ci:pkg:manage`, `ci:build:run`, `ci:build:stop` | `ALL` | 首期仍允许全局构建/编辑，并可见未审核项目 |
| `publisher` | `agent:app:read`, `ci:publish:read`, `ci:publish:preview`, `ci:publish:submit`, `ci:publish:stop` | `CUSTOM` | 只对被授权项目生效；默认只能看到已审核项目 |
| `apikey_manager` | `apikey:read`, `apikey:create`, `apikey:delete` | `ALL` | API Key 独立能力，不再塞进只读机器人 |
| `admin` | `*` | `ALL` | 超级管理员，走统一机器人链路，不走代码特判 |

说明：

- `viewer` 不再携带 `apikey:create/delete`
- `builder_global` 是首期简化方案，不代表未来必须全局
- 如果后续要收紧构建权限，可新增自定义 `builder_xxx` 机器人并把 `scopeMode` 改成 `CUSTOM`
- `agent:app:delete` 不默认放进 `builder_global`，如需删除能力，单独授予自定义机器人
- `publisher` 默认不带 `agent:app:read_unapproved`，因此默认看不到未审核项目
- 如果后续要给审核员、研发、运营放开未审核项目可见性，单独授予 `agent:app:read_unapproved`
- 本期产品决策：允许“先给 publisher 授权 scope，再等待项目审核通过”；但在审核通过前，publisher 默认看不到该项目

### 4.2 自定义机器人

管理员可以创建自定义机器人：

- 选择权限集合
- 选择 `scopeMode`
  - `ALL`
  - `CUSTOM`
- 当 `scopeMode=CUSTOM` 时，维护覆盖项目列表

典型场景：

- 某条发布线只允许发 5 个项目
- 某外包团队只能编辑指定项目
- 某审计用户只能读项目，不允许构建/发布

### 4.3 本期涉及的关键原子权限

为避免文档里提到能力但没定义权限码，本期至少明确这些原子权限：

| 权限码 | 含义 |
|------|------|
| `agent:app:read` | 查看项目详情、列表、构建产物 |
| `agent:app:read_unapproved` | 额外允许查看 `PENDING / REJECTED` 项目 |
| `agent:app:upload` | 上传/覆盖代码包 |
| `agent:app:write` | 修改项目元信息 |
| `agent:app:delete` | 删除项目 |
| `ci:pkg:manage` | 安装依赖、删除 dist、其他构建产物管理操作 |
| `ci:build:run` | 发起构建 / 安装并构建 / 批量构建 |
| `ci:build:stop` | 停止构建 / 停止批量构建 |
| `ci:publish:read` | 查看发布结果、二维码、批量发布结果 |
| `ci:publish:preview` | 发起预览发布 |
| `ci:publish:submit` | 发起正式发布 |
| `ci:publish:stop` | 停止发布 / 停止批量发布 |
| `admin:package:review` | 审核项目（APPROVE / REJECT） |
| `admin:robot:read` | 查看机器人列表、详情、权限、scope、绑定关系 |
| `admin:robot:write` | 创建、修改、删除机器人 |
| `admin:robot:assign` | 给用户绑定/解绑机器人，维护机器人与用户关系 |

### 4.4 初始化策略

由于老用户可以直接删除，本期不做旧角色兼容。

建议做法：

1. 清空旧用户及其 `sys_user_role` 绑定
2. 删除旧的 `default/product/dev/admin` 角色语义
3. 在 `robot` 表中直接按机器人模型重建预置角色
4. 新用户、新管理员全部只绑定新机器人

也就是说，本期系统里只有一种语义：

- 物理表上叫 `robot`
- 业务上也叫“机器人”

## 5. 业务流程

### 5.1 新项目上传与审核

```text
用户上传代码
  ↓
创建 miniapp_package，review_status = PENDING
  ↓
若用户有 builder_global，可继续安装/构建/编辑
  ↓
普通用户若没有 publisher 对该项目的 scope，不能发布
  ↓
即使用户有 publisher scope，只要 review_status != APPROVED，仍然不能发布
  ↓
管理员审核
  ↓
review_status = APPROVED / REJECTED
```

关键点：

- “能不能发”取决于两个条件：`publisher scope` + `review_status`
- 审核通过时只改项目状态，不自动改机器人 scope
- 是否把项目加入某个发布机器人，属于授权动作，不是审核动作
- 本期审核粒度是 `packageId`，不是“某个构建版本”
- 同一个 `packageId` 下上传新代码，不自动把 `review_status` 重置回 `PENDING`
- 即使管理员已提前把项目加入 publisher scope，只要 publisher 没有 `agent:app:read_unapproved`，在审核通过前仍然看不到该项目

本期明确规则：

- `PENDING` / `REJECTED` 项目都可以再次提审
- 审核动作由管理员触发
- 如果未来需要“每个版本独立审核”，再新增版本级审核表，不在本期范围内

可见性默认分层：

- `admin`：能看到所有状态项目
- 带 `agent:app:read + agent:app:read_unapproved` 的用户：能看到所有状态项目
- 只有 `agent:app:read` 的用户：只能看到 `APPROVED` 项目

### 5.2 用户开通权限

```text
用户注册
  ↓
默认绑定 viewer
  ↓
如需 API Key，额外绑定 apikey_manager
  ↓
如需构建能力，绑定 builder_global 或自定义 builder 机器人
  ↓
如需发布能力，绑定 publisher，并配置可发项目范围
```

### 5.3 管理员授权某个项目可发布

授权动作与审核动作分开：

```text
管理员审核项目
  ↓
项目 review_status = APPROVED
  ↓
管理员决定哪些发布机器人可以覆盖该项目
  ↓
将 packageId 加入对应 publisher 机器人的 scope 列表
```

这样能支持：

- 项目审核通过，但暂时没人有权发
- 同一个审核通过项目，只开放给部分发布线

### 5.4 删除项目

删除项目走独立权限：

```text
用户发起删除
  ↓
校验同一个机器人内是否拥有 agent:app:delete
  ↓
本期不检查 review_status
  ↓
执行软删或硬删
  ↓
若为软删：保留 robot_scope 记录
若为硬删：同步清理 robot_scope 记录
```

本期明确规则：

- 删除不需要额外审批
- 删除前端需要二次确认
- 是否允许某类用户删除项目，完全由 `agent:app:delete` 是否授予决定

## 6. 数据模型

### 6.1 `robot`

```sql
CREATE TABLE robot (
    id          BIGINT AUTO_INCREMENT PRIMARY KEY,
    code        VARCHAR(64) NOT NULL UNIQUE COMMENT '机器人编码',
    name        VARCHAR(64) NOT NULL COMMENT '机器人名称',
    description VARCHAR(256) DEFAULT NULL COMMENT '描述',
    scope_mode  VARCHAR(16) NOT NULL DEFAULT 'ALL' COMMENT 'ALL/CUSTOM',
    builtin     TINYINT(1) NOT NULL DEFAULT 0 COMMENT '是否预置',
    enabled     TINYINT(1) NOT NULL DEFAULT 1 COMMENT '是否启用',
    created_at  DATETIME DEFAULT CURRENT_TIMESTAMP,
    updated_at  DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
);
```

字段含义：

- `scope_mode=ALL`：对该资源类型全量生效
- `scope_mode=CUSTOM`：只对 scope 表里的项目生效
- `builtin=1`：预置机器人
- `enabled=1`：启用状态

### 6.2 `robot_permission`

```sql
CREATE TABLE robot_permission (
    id              BIGINT AUTO_INCREMENT PRIMARY KEY,
    robot_code      VARCHAR(64) NOT NULL,
    permission_code VARCHAR(128) NOT NULL,
    UNIQUE KEY uk_robot_perm (robot_code, permission_code)
);
```

### 6.3 `robot_scope`

```sql
CREATE TABLE robot_scope (
    id          BIGINT AUTO_INCREMENT PRIMARY KEY,
    robot_code  VARCHAR(64) NOT NULL COMMENT '机器人 code',
    resource_type VARCHAR(32) NOT NULL DEFAULT 'PACKAGE' COMMENT '资源类型，首期固定 PACKAGE',
    resource_id VARCHAR(64) NOT NULL COMMENT '资源ID，首期存 packageId',
    created_at  DATETIME DEFAULT CURRENT_TIMESTAMP,
    UNIQUE KEY uk_robot_res (robot_code, resource_type, resource_id)
);
```

说明：

- 只有 `scope_mode=CUSTOM` 的机器人才使用这张表
- `scope_mode=ALL` 不写 `*`，也不往表里插全量记录
- 首期只使用 `resource_type='PACKAGE'`
- 预留 `resource_type` 是为了后续支持模板/资源组/租户等新资源类型
- 项目软删时保留 scope 记录，方便恢复
- 项目硬删时同步清理 scope 记录，另配一条巡检/修复脚本兜底现网脏数据

### 6.4 `user_robot`

```sql
CREATE TABLE user_robot (
    id          BIGINT AUTO_INCREMENT PRIMARY KEY,
    user_id     BIGINT NOT NULL,
    robot_code  VARCHAR(64) NOT NULL,
    created_at  DATETIME DEFAULT CURRENT_TIMESTAMP,
    UNIQUE KEY uk_user_robot (user_id, robot_code)
);
```

### 6.5 在 `miniapp_package` 上增加审核字段

```sql
ALTER TABLE miniapp_package
    ADD COLUMN review_status  VARCHAR(16) NOT NULL DEFAULT 'PENDING' COMMENT 'PENDING/APPROVED/REJECTED',
    ADD COLUMN reviewed_by    BIGINT DEFAULT NULL COMMENT '审核人',
    ADD COLUMN reviewed_at    DATETIME DEFAULT NULL COMMENT '审核时间',
    ADD COLUMN review_comment VARCHAR(256) DEFAULT NULL COMMENT '审核备注';
```

说明：

- 历史存量项目迁移时默认置为 `APPROVED`
- 新上传项目默认 `PENDING`
- 审核以 `packageId` 为粒度，不区分版本
- 同一 `packageId` 下后续上传新代码，本期不自动重置 `review_status`

### 6.6 `user_op_log` 增加授权上下文字段

不建议只加单个 `robot_code`，因为批量请求可能同时命中多个机器人。

建议新增：

```sql
ALTER TABLE user_op_log
    ADD COLUMN auth_context JSON DEFAULT NULL COMMENT '本次请求的授权上下文';
```

示例：

```json
{
  "permission": "ci:publish:submit",
  "packageIds": ["pkg_001", "pkg_002"],
  "matchedRobots": {
    "pkg_001": ["publisher_a"],
    "pkg_002": ["publisher_b", "publisher_backup"]
  }
}
```

说明：

- `matchedRobots` 记数组而不是单值
- 同一个 `packageId` 命中多个机器人时全部记录，便于事后审计和回收授权分析

## 7. 后端改造点

### 7.1 不再只靠 `PermissionService.hasPermission(userId, code)`

现有接口只支持“用户是否拥有权限码”，签名不够表达资源范围。

需要新增资源级接口：

```java
boolean hasPermission(Long userId, String permissionCode, String packageId);

void assertHasPermission(Long userId, String permissionCode, String packageId);

Map<String, Boolean> batchCheck(Long userId, String permissionCode, List<String> packageIds);

boolean isPackageVisible(Long userId, String packageId);
```

其中 `hasPermission/assertHasPermission` 的实现约束：

- 底层必须是“单机器人闭包”判定
- `admin` 通过 `* + ALL` 命中，不准代码旁路
- 资源级查询结果建议单独缓存，不与 `/permission/my` 的用户全局权限缓存混用
- `isPackageVisible` 的语义是“该用户能不能看到这个项目”
- `isPackageVisible` 必须把 `review_status` 纳入判定，而不是只看 `agent:app:read`

推荐语义写死为：

```java
isPackageVisible(userId, packageId)
  =
  hasPermission(userId, "agent:app:read", packageId)
  &&
  (
    reviewStatus(packageId) == APPROVED
    || hasPermission(userId, "agent:app:read_unapproved", packageId)
  );
```

说明：

- `isPackageVisible` 是“可见性”判定
- `hasPermission(userId, "agent:app:read", packageId)` 是“读权限”判定
- 两者相关，但不是同一个概念
- 资源级鉴权仅适用于 `packageId` 相关接口
- 像 API Key、机器人管理、用户管理这类不关联 `packageId` 的接口，继续使用全局权限判定

### 7.2 AOP 只适合做粗粒度，资源级鉴权建议注解版和显式调用并存

原因：

- `packageId` 可能在 path 中
- 也可能在 body 中
- 也可能要先通过 `taskId` 反查

所以本期建议：

- 继续保留 `@RequirePermission` 做无资源上下文的粗粒度能力校验
- 对能直接从 path/body 取到 `packageId` 的接口，优先增加资源版注解
- 对 `taskId -> packageId(s)` 这类要先反查资源的接口，退回 Service 显式调用

建议新增：

```java
@RequireResourcePermission(value = "ci:publish:submit", resource = "#packageId")
```

这样能减少“开发忘记在 Service 里补资源鉴权”的漏口。

### 7.3 `/api/admin/permission/my` 保留，但用途收缩

返回仍是权限码数组，用于：

- 页面级菜单显隐
- 大类按钮显隐

不再用于：

- 单项目按钮是否可点
- 批量操作的项目筛选
- 任何针对具体 `packageId` 的显示/隐藏/放行动作

### 7.4 项目接口返回 `allowedPermissions`

建议改造：

- `GET /api/app/list?reviewStatus=`
- `GET /api/app/{packageId}`

由后端直接返回该用户对当前项目的资源级权限码集合。

这样前端不必自己推导复杂的 `permission + scope + review_status` 组合。

其中：

- 不传 `reviewStatus`：返回当前用户可见的全部项目
- 传 `APPROVED/PENDING/REJECTED/ALL`：只对当前用户可见集合做二次筛选
- `reviewStatus` 参数不能突破可见性边界

如果前端仍然想展示成按钮布尔值：

- 由前端基于 `allowedPermissions + reviewStatus` 做本地映射
- 不再让后端维护一份与权限码平行的 `allowedActions` 布尔结构

但前提是：

- 该项目已经先通过 `isPackageVisible(userId, packageId)` 判定为可见
- 对不可见项目，不返回详情，也不返回 `allowedPermissions`

### 7.5 新增审核接口

```text
GET  /api/admin/package/review/pending
POST /api/admin/package/{packageId}/review
```

推荐权限控制：

- `GET /api/admin/package/review/pending`
  - 需要 `admin:package:review`
- `POST /api/admin/package/{packageId}/review`
  - 需要 `admin:package:review`

请求体示例：

```json
{
  "action": "APPROVE",
  "comment": "代码结构符合规范",
  "expectedStatus": "PENDING"
}
```

约束：

- 支持 `PENDING -> APPROVED/REJECTED`
- 支持 `REJECTED -> APPROVED/REJECTED`
- `expectedStatus` 用于防止并发双审导致的状态覆盖

### 7.6 机器人管理接口

接口沿用原方案，但底层直接操作 `robot*` / `user_robot` 表：

```text
GET    /api/admin/robot/list
POST   /api/admin/robot
PUT    /api/admin/robot/{code}
DELETE /api/admin/robot/{code}

GET    /api/admin/robot/{code}/permissions
PUT    /api/admin/robot/{code}/permissions

GET    /api/admin/robot/{code}/scope
PUT    /api/admin/robot/{code}/scope
POST   /api/admin/robot/{code}/scope/batch-add
POST   /api/admin/robot/{code}/scope/batch-remove
DELETE /api/admin/robot/{code}/scope/{packageId}
```

推荐权限控制：

- `admin:robot:read`
  - 查看机器人列表、详情、权限、scope、绑定关系
- `admin:robot:write`
  - 创建、修改、删除机器人，修改权限集合
- `admin:robot:assign`
  - 给用户绑定/解绑机器人，维护 scope

### 7.7 缓存失效矩阵

新模型下影响资源级判定结果的不只是 `user_robot`。

建议至少拆两层缓存：

- `userPermissionsCache`
  - 仅缓存 `/permission/my` 这类“用户全局权限码集合”
- `resourceAuthorizationCache`
  - 缓存 `(userId, permissionCode, packageId)` 级别的存在性判定，或列表页的 `allowedPermissions`

失效矩阵：

| 变更类型 | 影响范围 | 建议失效 |
|--------|--------|---------|
| `user_robot` 绑定变化 | 单个用户 | 清该用户两层缓存 |
| `robot_permission` 变化 | 所有绑定该机器人的用户 | 反查绑定用户并清两层缓存 |
| `robot_scope` 变化 | 所有绑定该机器人的用户 | 反查绑定用户并清 `resourceAuthorizationCache`，必要时顺带清全局权限缓存 |
| `robot.enabled` / `scope_mode` 变化 | 所有绑定该机器人的用户 | 反查绑定用户并清两层缓存 |
| `miniapp_package.review_status` 变化 | 访问该项目的用户 | 清该项目相关的 `resourceAuthorizationCache` / 列表页缓存；不必清 `/permission/my` |

实现建议：

- 如果一期不做 `resourceAuthorizationCache`，那至少把失效矩阵写进文档，避免后续引缓存时遗漏
- 所有“按角色反查用户”的清缓存动作建议异步化，避免管理台写操作阻塞

## 8. 前端接入要点

### 8.1 页面级能力仍看 `/permission/my`

例如：

- 能不能看到“机器人管理”页
- 能不能看到“审核中心”页

但只要页面上的交互目标落到某个具体 `packageId`，前端就必须改用项目接口返回的资源级结果。

### 8.2 项目级按钮看后端返回的 `allowedPermissions + reviewStatus`

例如列表行上的：

- 构建
- 发布预览
- 正式发布
- 删除

都不再由前端拿 `/permission/my` 自己拼装判断。

### 8.3 机器人管理页需明确区分两件事

- **审核项目**：改 `review_status`
- **授权项目**：把 `packageId` 加入某个机器人的 scope

这两个动作不能混成一个按钮。

## 9. 迁移策略

### 9.1 第一步：清理旧用户和旧绑定

既然老用户可以直接删除，本期按一次性切换处理：

1. 删除旧用户
2. 清空旧 `sys_user_role`
3. 停用旧的 `default/product/dev/admin` 角色语义

这样做的结果是：

- 不再需要旧角色兼容
- 不再需要“老角色和新机器人并存”
- 不再需要逐步迁移用户

### 9.2 第二步：创建新表并切换代码

1. 创建 `robot`
2. 创建 `robot_permission`
3. 创建 `robot_scope`
4. 创建 `user_robot`
5. 给 `miniapp_package` 加审核字段
6. 给 `user_op_log` 加 `auth_context`
7. 后端代码改为只读写新表

### 9.3 第三步：初始化预置机器人

插入：

- `viewer`
- `builder_global`
- `publisher`
- `apikey_manager`
- `admin`

并初始化它们的权限集合与默认 scope 策略。

### 9.4 第四步：删除旧 `sys_*` 表

在新链路跑通后，直接删除：

- `sys_role`
- `sys_role_permission`
- `sys_user_role`
- 其他仅服务于旧权限模型的 `sys_*` 表

### 9.5 第五步：实现资源级鉴权服务

改造后端：

- 单项目接口按 `packageId` 鉴权
- 任务/二维码接口按 `taskId -> packageId(s)` 反查后鉴权
- 列表接口只返回可读项目
- 批量接口逐项目鉴权
- 移除 `isAdmin -> 直接放行` 之类的代码旁路

### 9.6 第六步：上线审核流

规则：

- 历史项目统一置为 `APPROVED`
- 新上传项目默认 `PENDING`
- 发布链路开始强制检查 `review_status`

上线方式建议：

- 提前公告：审核上线后，新上传且未审核的项目会被阻止发布
- 灰度期可先“命中未审核只告警不拦截”，确认流程跑通后再切硬拦截

### 9.7 第七步：创建新用户与管理员

由于旧用户已清空，这一步只做新体系初始化：

- 普通新用户默认写入 `user_robot -> viewer`
- 需要 API Key 的用户额外绑定 `apikey_manager`
- 需要构建能力的用户绑定 `builder_global` 或自定义 builder 机器人
- 管理员绑定 `admin`
- 需要发布能力的用户绑定 `publisher` 并配置 scope

### 9.8 第八步：收尾清理

执行前提：

- 旧用户和旧角色语义都已经清空
- 新 `robot*` / `user_robot` 链路已经稳定运行一段观察期
- 审计、缓存、管理台接口都不再依赖旧 `sys_*` 权限表

收尾动作：

- 删除旧迁移脚本和旧表访问代码
- 删除代码里所有 `sys_role*` / `sys_user_role` 常量与 Mapper
- 清理旧权限模型相关文档

## 10. 后续扩展

如果未来需要“同一个机器人下，不同用户能操作不同项目”，再引入用户级 scope：

```sql
CREATE TABLE user_robot_scope (
    id          BIGINT AUTO_INCREMENT PRIMARY KEY,
    user_id     BIGINT NOT NULL,
    package_id  VARCHAR(64) NOT NULL,
    created_at  DATETIME DEFAULT CURRENT_TIMESTAMP,
    UNIQUE KEY uk_user_pkg (user_id, package_id)
);
```

届时鉴权公式升级为：

```text
存在某个机器人 R：
  R 包含权限 P
  且 R 覆盖 packageId
  且 user_scope 覆盖 packageId
```

但这属于二期，不进入本期实现。
